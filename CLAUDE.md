# Контекст проекта (для Claude и для команды)

Claude Code читает этот файл автоматически, когда открывают папку проекта. Архитектура, метрики, нормативы и
деплой описаны в [README.md](README.md), [BACKEND.md](BACKEND.md) и [ml/README.md](ml/README.md). Здесь — то,
чего там нет: правила работы, текущее состояние и договорённости команды.

## Проект

- Кейс ForteBank Datathon 26: сервис по видеозаписи кассы выдаёт вердикт и нарушения (тип, таймкод,
  описание, 1–3 кадра, норматив РК). Условие кейса — `Кейс_ForteBank.docx` (у владельца, в git не входит).
- Главное из ТЗ:
  - API `POST /api/v1/analyze` (поле `file`, заголовок `X-API-Key`) возвращает `job_id`;
  - `GET /api/v1/jobs/{id}` возвращает `processing` / `done` / `failed` и результат по схеме раздела 10;
  - не больше 5 минут на видео, обязателен публичный URL;
  - всё работает локально, без облачных AI-API; лица не распознаются, звук не анализируется;
  - только open source с коммерческой лицензией; нормативы — только акты РК;
  - пропуск нарушения недопустим, ложных срабатываний — минимум;
  - финальное видео будет снято под другим углом, возможны новые типы нарушений;
  - дедлайн сдачи — 12:00.
- Принцип владельца: «если условиями прямо не запрещено — можно». Задавать вопросы, пока нет уверенности ~95 %.

## Обязательные правила

1. **Тестовые видео жюри** (на поде в `/workspace/jobs`):
   - не открывать и не смотреть их кадры, не делать скриншоты результатов с их кадрами;
   - не передавать никаким внешним ИИ, включая Claude;
   - не использовать для обучения и не публиковать (р. 10 ТЗ).

   С ними работает только код на поде; смотреть можно лишь метаданные и время обработки.
2. **В git не попадают:** датасет, веса, `.env`, ключ API жюри, IP и порт SSH пода.
3. **Пароли, логины и оплату** (GitHub, RunPod) вводит только владелец.
4. **Только после явного «да» владельца:** остановка или удаление пода, удаление данных, смена ключа API.
5. **Данные — только в рамках хакатона.** После него удалить:
   - под (Terminate);
   - `dataset/` и копии видео на флешке;
   - `%TEMP%\fbk` на старом ноутбуке.

## Кто что делает

- **Владелец репозитория** — ML-модель, а с 18.10 также сервер и интерфейс (`app/`, `web/`).
- **Второй участник** — бэкенд. Доступ к репозиторию и поду ему выдаёт владелец.

## Где что работает

- **Под RunPod**, NVIDIA L40S 48 ГБ, около $1.10 в час.
  - Публичный адрес: `https://<POD_ID>-8080.proxy.runpod.net` (`POD_ID` — в карточке пода).
  - SSH-команда — на вкладке **Connect**; порт меняется после каждого перезапуска пода.
- **SSH-ключи:** ключ второго ноутбука (`user@DESKTOP-GJ1499L`) добавлен на под вручную. После Stop/Start
  пода он пропадёт, если его нет в RunPod → **Settings → SSH Public Keys**.

| Путь на поде | Что там |
|---|---|
| `/workspace/forte-app` | развёрнутая копия репозитория (копия файлов, не git-клон) + `.env` с ключом жюри |
| `/workspace/forte` | эксперименты: `dataset/`, `eval/out/` (кэши прогонов), `ml/` |
| `/workspace/venv`, `/workspace/env.sh` | Python-окружение (vLLM, FastAPI…); `source /workspace/env.sh` его подключает |
| `/workspace/hf` | веса Qwen3-VL-30B-A3B-FP8 и 32B-FP8 (кэш Hugging Face, работает офлайн) |
| `/workspace/jobs` | загруженные видео и результаты, удаляются через 72 ч |
| `/workspace/logs/vllm.log`, `/workspace/logs/api.log` | логи модели и сервера |

Модель и сервер запущены через `nohup` и от ноутбука не зависят. После Stop/Start пода их нужно запустить
заново (модель грузится 2–3 мин):

```bash
bash /workspace/forte-app/ml/remote/serve_vllm.sh
until curl -sf 127.0.0.1:8000/v1/models >/dev/null; do sleep 5; done
cd /workspace/forte-app && bash ml/remote/start_api.sh
```

Выкатить изменения кода на под — из Git Bash в папке репозитория. `.env` на поде при этом не меняется:

```bash
git ls-files -z | tar --null -cf - -T - | ssh root@<IP> -p <PORT> -i ~/.ssh/id_ed25519 \
  'tar --no-same-owner -xf - -C /workspace/forte-app && cd /workspace/forte-app && bash ml/remote/start_api.sh'
```

## Подводные камни (уже наступали)

- **Прокси RunPod** обрывает запрос через 100 с — поэтому API асинхронный. Сервер должен слушать `0.0.0.0`.
- **`pkill -f ...` внутри `ssh '...'`** убивает саму ssh-команду. Останавливать процессы только через
  скрипты `serve_vllm.sh` и `start_api.sh`.
- **Кэш Hugging Face** хранит файлы в `/workspace/hf/hub/blobs`: удаление папки модели место не освобождает.
  Диск `/workspace` — 100 ГБ, занят примерно на 74 %.
- **Системный pip на поде** заблокирован (PEP 668) — ставить пакеты только в `/workspace/venv`.
- **Ответы модели слегка разные** от прогона к прогону: вердикт может меняться у 1–2 роликов из 39.

## Модель: что решено

- **Финальная схема:**
  - модель — Qwen3-VL-30B-A3B-Instruct-FP8 (Apache-2.0) в vLLM;
  - поиск окнами по 10 с с шагом 5 с, 2 кадра в секунду;
  - повторная проверка типов T1, T4, T5, T8, T9, T13;
  - каталог типов и нормативов — `ml/cashier/violations.yaml`;
  - метрики и методика оценки — `ml/README.md`, раздел 5.
- **Железо не меняем:** владелец решил, что текущей точности достаточно для презентации.
- **Что отклонено** (подробнее — `ml/README.md`, «Что пробовали»):
  - обычный классификатор — данных слишком мало;
  - EmbeddingGemma 2 — слабо различает нарушения;
  - YOLO/Ultralytics — лицензия AGPL; D-FINE — не нужен в текущей схеме;
  - Qwen3-VL-8B — много пропусков;
  - Qwen3-VL-32B — нужно 80 ГБ, не укладывается в лимит при 5 видео разом;
  - Gemma 4 26B-A4B — слабее;
  - промпт «в наблюдении только видимые действия» — точность упала с 61,5 до 46,2 %; вместо него
    фильтр `observation_ok` в `pipeline.py`;
  - перенос «следующий клиент входит, деньги не убраны» из T2 в T11 — пропусков стало больше;
  - v2 «память примеров» на V-JEPA 2 (21.10): эмбеддинги не отличают нарушение от нормы (AUC ≈ 0,54),
    а показ размеченных примеров при повторной проверке даёт разницу в пределах разброса между запусками.
    Код оставлен как эксперимент (`ml/cashier/memory.py`, `references` в `verify.py`), в продукт не вошёл.
  - голосование повторной проверки (большинство из 3): 65,1 % против 63,6 % у одного запуска — в пределах
    шума; ошибки систематические (ответ меняется лишь у 10 кандидатов из 98).
- **Разброс между запусками заметный:** один и тот же вариант даёт 61,5–64,1 % по вердикту. Сравнивать
  варианты только по нескольким запускам.
- **Промпты и политику проверки менять только с повторной оценкой на всём датасете**: на поде
  `ml/experiments/vlm_eval.py`, `verify_eval.py`, `policy_eval.py`.

## Разметка команды (`eval/labels.csv`)

- Организаторы дают только «нарушение / нет» и секунду; типы нарушений размечены командой.
- `X-47` ≡ `X-4`, `X-48` ≡ `X-5` — побайтные дубли.
- **`X-4`** (57 с): пачка денег предыдущего клиента не убрана в сейф, входит следующий клиент. По разметке это
  T11, но модель называет это T2. Поэтому в каталоге и T2, и T11 сформулированы через «наличные не убраны в сейф».
- **`X-39`** — спорный: по разметке норма, но удостоверение не предъявляется, как в `X-2` с нарушением.
  Исключён из подсчёта.
- **`X-1`** — возврат денег после пересчёта (T12, «требует сверки»: допустимо только при излишке).
- **`X-2`** — нет удостоверения. **`X-34`** — нет удостоверения, и клиент ушёл до конца операции.
- **`X-15`** — инкассаторская сумка с деньгами оставлена на столе.
- **`X-13`, `X-24`, `X-28`** — смысл нарушения неясен, разметка — версия команды.

## Известные проблемы

- Ложное T2 в `X-4` на 5 с: модель «видит» второго человека, когда входит первый клиент.
- Пропуски:
  - `X-2` — T9;
  - `X-11` — T1, тёмная комната;
  - `X-22`, `X-24`, `X-28` — ключ в замке сейфа, деталь в несколько пикселей;
  - `X-44` — T8.
- Когда роликов много, у последних в очереди может не хватить времени на повторную проверку — тогда больше
  лишних тревог. 10 длинных роликов разом укладываются в 233 с из 300.

# ML-модуль: распознавание нарушений кассовой дисциплины по видео

Модуль принимает видеозапись кассы (.mov) и возвращает вердикт, список возможных нарушений с типом,
таймкодом, описанием, 1–3 кадрами-доказательствами и ссылкой на норматив РК — в формате раздела 10 ТЗ.
Все модели работают локально внутри сервиса; обращений к облачным AI-сервисам нет.

Результат — **подсказка для проверяющего**, а не юридическое заключение: описание формулируется только
через видимое, а типы, где вывод требует невидимых данных (суммы, документы), помечаются как требующие сверки.

---

## 1. Архитектура

```
 видео (.mov)
   │  OpenCV: 2 кадра/с, длинная сторона 848 px
   ▼
 ┌──────────────────────────── Ступень 1 — поиск кандидатов ─────────────────────────────┐
 │ окна по 10 с с шагом 5 с (≈20 кадров с подписями времени)                              │
 │ Qwen3-VL-30B-A3B (через локальный vLLM) + чек-лист типов T1–T13 + «иное»               │
 │ → JSON: тип, кадр начала, уверенность, наблюдение (по-русски)                         │
 │ слияние одинаковых типов ближе 4 с                                                     │
 └─────────────────────────────────────────────────────────────────────────────────────────┘
   │ кандидаты
   ▼
 ┌──────────────────────────── Ступень 2 — проверка «рискованных» типов ─────────────────┐
 │ для T1, T4, T5, T8, T9, T13: клип вокруг таймкода; модель находит кассира/стол/сейф │
 │ (координаты), нужная область вырезается и увеличивается;                              │
 │ узкий вопрос по типу; для T1 и T9 — набор простых подвопросов, решение в коде          │
 │ (например, T1: «уходит ли кассир?» + «открыт ли сейф?» + «деньги на столе?»)           │
 └─────────────────────────────────────────────────────────────────────────────────────────┘
   │ подтверждённые + не требующие проверки
   ▼
 кадры-доказательства (событие, −1,5 с, +1,5 с) → описание из наблюдения + пояснение + норматив
   ▼
 {"verdict", "violations": [...], "details": [...], "timing": {...}}
```

**Почему так.** Модель хорошо замечает отдельные действия (вошёл человек, пьёт из стакана, инкассатор
ушёл), но склонна «видеть» нарушения там, где их нет. Первая ступень настроена на полноту (пропуск хуже
ложной тревоги — FAQ 16), вторая отсекает ложные срабатывания там, где их больше всего: телефон, купюра
в одежду, уход с рабочего места, проверка удостоверения.

**Таймкод события** — кадр, на который указала модель в своём окне (точность — см. раздел 5).
**Нарушения «по бездействию»** (не проверено удостоверение, инкассатор ушёл до проверки) получают
таймкод момента, когда должно было произойти обязательное действие, — передачи наличных или ухода.

## 2. Модели и лицензии

| Компонент | Что делает | Лицензия |
|---|---|---|
| **Qwen3-VL-30B-A3B-Instruct-FP8** (Alibaba Qwen) | обе ступени: поиск и проверка | Apache-2.0 |
| vLLM 0.31 | локальный сервер инференса (OpenAI-совместимый API на 127.0.0.1) | Apache-2.0 |
| OpenCV | чтение видео, кадры, JPEG | Apache-2.0 |

Веса скачиваются один раз; после этого сервис работает без интернета (`HF_HUB_OFFLINE=1`) — его можно
перенести во внутренний контур банка. Распознавания и идентификации лиц нет.

## 3. Железо и скорость

- GPU: 1× NVIDIA L40S 48 ГБ (RunPod). Модель занимает ~30 ГБ, остальное — кэш внимания.
- Один ролик: ~6–10 с на поиск + несколько секунд на проверку.
- **5 самых длинных роликов датасета одновременно (431 с видео): последний готов через 115 с** при лимите 300 с.
- Защита по времени: если до бюджета (240 с) остаётся меньше 60 с, проверка пропускается и кандидаты
  отдаются как есть (лучше лишняя тревога, чем отсутствие ответа).

## 4. Как запустить

На GPU-сервере (один раз):

```bash
bash ml/remote/setup_pod.sh            # окружение в /workspace/venv, vLLM, веса модели
MAXLEN=16384 GPU_UTIL=0.92 bash ml/remote/serve_vllm.sh Qwen/Qwen3-VL-30B-A3B-Instruct-FP8
```

Проверка на одном ролике:

```bash
python -m ml.cashier.pipeline dataset/videos/X-46.mov
```

### Контракт для бэкенда

```python
from ml.cashier.pipeline import Config, analyze

result = analyze("/workspace/jobs/<id>/input.mov",
                 Config(api="http://127.0.0.1:8000"),        # где слушает vLLM
                 progress=lambda frac, stage: ...)           # необязательно: 0..1 и подпись этапа для UI
```

Возвращает словарь:

| Поле | Для чего |
|---|---|
| `verdict` | `"violation"` / `"no_violation"` — **в API жюри** |
| `violations[]` | `type`, `timecode_sec`, `description`, `evidence_frames[]` (`timestamp_sec`, `image_base64`) — **в API жюри как есть** |
| `details[]` | по тому же индексу: `type_id` (T1…), `confidence`, `observation`, `why`, `sources[]` (документ, пункт, цитата, ссылка, основание), `verified` — для интерфейса |
| `timing` | длительность ролика и время этапов — для логов |

Ошибка открытия видео → `ValueError` с понятным текстом (бэкенд ставит задаче `failed`).
Функция блокирующая; одновременно можно вызывать для нескольких роликов — vLLM сам батчит запросы.

## 5. Результаты на обучающем датасете

Методика: 42 ролика, из них `X-47` ≡ `X-4` и `X-48` ≡ `X-5` (побайтные дубли — объединены, у `X-4` два
события), `X-39` исключён как спорный (по разметке «норма», но удостоверение не предъявляется, как в
`X-2` с нарушением). Итого **39 роликов: 22 события нарушений, 17 нормальных роликов**.
Событие найдено, если предсказание в пределах ±3 с от метки; тип — если совпал тип в этом окне.
Типы нарушений размечены командой (организаторы дают только «нарушение/нет» и секунду).

### Итог финальной версии (Qwen3-VL-30B-A3B → проверка T1, T4, T5, T8, T9, T13)

| Метрика | Значение |
|---|---|
| Вердикт на ролик верен | **24 из 39 (61,5 %)** |
| Ролики с нарушением, где сервис ничего не нашёл | 6 из 21 |
| Нормальные ролики с ложной тревогой | 9 из 17 |
| События, найденные в пределах ±3 с | 9 из 22 |
| …из них с верным типом | 8 |
| Ошибка таймкода у найденных событий | 0–2,6 с, медиана ≈ 1 с |
| Время на ролик (поиск) | 6,3 с в среднем, 28 с на самом длинном (143 с) |
| 5 самых длинных роликов одновременно | 115 с (лимит 300 с) |

Где ошибается:

- **Пропуски:** `X-22`, `X-24`, `X-28` — ключ оставлен в сейфе (T13, деталь в несколько пикселей);
  `X-11` — уход из тёмной комнаты при открытом сейфе; `X-44` — купюра в рукав; `X-2` — приём наличных
  без удостоверения.
- **Проверка T5 (еда/напитки)** добавлена после ручного теста: на `X-1` кассир подносит купюры к лицу
  (смотрит на просвет), поиск принял это за еду; проверка такой эпизод отклоняет («работает с деньгами»),
  а настоящее питьё в `X-46` подтверждает. Метрики по вердикту не меняются.
- **Ложные тревоги:** «телефон» на кадрах с мелкими предметами (`X-10`, `X-14`, `X-27`), «возврат денег»
  при пересчёте (`X-14`, `X-43`), «инкассатор ушёл» (`X-14`, `X-16`), «нет удостоверения» (`X-19`, `X-35`).
- Типы, которые находятся уверенно: посторонний в кассе (T2, 4 из 4), инкассатор ушёл до проверки сумки (T7),
  личные вещи на столе (T6), телефон в руках (T4), клиент ушёл до конца пересчёта (T10).

Модель отвечает с температурой 0, но из-за пакетной обработки в vLLM повторный прогон того же ролика может
дать немного другие кандидаты: разброс между прогонами — 1–2 ролика по вердикту.

### Сравнение с альтернативами (те же 39 роликов)

| Схема | Пропуски | Ложные | Вердикт | Скорость / железо |
|---|---|---|---|---|
| Только поиск 30B, без проверки | 1 | 18 | 51 % | быстро, L40S |
| **30B → проверка 30B (финальная)** | **6** | **9** | **61,5 %** | 5 роликов за 115 с, L40S 48 ГБ |
| 30B → проверка Qwen3-VL-32B | 7 | 4 | 71,8 % | нужна GPU 80 ГБ (две модели) |
| 32B → проверка 32B | 7 | 5 | 69,2 % | 5 роликов за 453 с — **не укладывается** в лимит на L40S |
| Gemma 4 26B-A4B → проверка Gemma | 12 | 6 | 53,8 % | быстро, L40S |

Путь развития без смены подхода: проверяющая модель 32B на GPU 80 ГБ (+10 п.п. по вердикту на наших данных),
увеличенные кропы сейфа для T13, уточнение таймкода по треку человека (детектор людей).

### Что пробовали и почему отказались

| Подход | Результат | Решение |
|---|---|---|
| EmbeddingGemma 2 (эмбеддинги кадров + текстовые запросы) | не отличает телефон / удостоверение / купюры; открытый сейф от закрытого — с минимальным запасом | не используем |
| Классификатор на замороженных признаках (SigLIP 2) | 1–6 примеров на класс, нет новых типов (FAQ 9) | отказались до обучения |
| Qwen3-VL-8B, «найди нарушение» по окнам | 13 пропусков из 22 | заменили на 30B |
| Покадровое восприятие (состояния) + правила по временной линии | мелкие детали (сейф, телефон, карточка) на целом кадре не различаются ни 8B, ни 30B | оставили правила как код (`rules.py`), в продукт не вошло |
| Qwen3-VL-32B (плотная) | лучший проверяющий (до 71,8 % в паре с 30B), но 5 роликов разом — 453 с > лимита; две модели не помещаются в 48 ГБ | вариант для GPU 80 ГБ |
| Gemma 4 26B-A4B | быстрая, но слабее в поиске (7 пропусков) | запасной проверяющий |
| Жёсткие требования к формулировке наблюдения в промпте поиска | вердикт 61,5 % → 46,2 % (модель стала давать больше кандидатов) | откатили; вместо этого фильтр наблюдений в коде |

## 6. Типы нарушений и нормативная база

Каталог — `ml/cashier/violations.yaml` (им пользуются и модель, и API). Тексты пунктов сверены по
зеркалу zakon.uchet.kz; перед сдачей пункты стоит ещё раз открыть на adilet.zan.kz.

- **[231]** Постановление Правления НБРК от 29.11.2019 № 231 «Правила осуществления кассовых операций и
  операций по инкассации банкнот, монет и ценностей…» — https://adilet.zan.kz/rus/docs/V1900019680
- **[14]** Постановление Правления НБРК от 24.02.2020 № 14 «Правила организации охраны и устройства
  помещений…» — https://adilet.zan.kz/rus/docs/V2000020075

| Код | Нарушение | Что видно на видео | Норматив | Основание |
|---|---|---|---|---|
| T1 | Оставление рабочего места без обеспечения сохранности | кассир уходит, наличные/сумка на столе или сейф открыт | [231] п. 20, п. 22 | прямое |
| T2 | Посторонний при открытых ценностях | входит человек, пока наличные лежат открыто | [231] п. 20; [14] п. 8 | трактовка |
| T3 | Дверь кассового помещения не закрыта | дверь остаётся открытой во время работы | [14] п. 8, подп. 1) п. 16 | трактовка |
| T4 | Смартфон на рабочем месте | телефон в руках кассира | [231] п. 12 | прямое (смартфон с камерой) |
| T5 | Еда/напитки на рабочем месте | кассир пьёт или ест у стола с наличными | [231] п. 12 | трактовка |
| T6 | Личные вещи на рабочем месте | сумка, одежда на столе | [231] п. 12 | прямое |
| T7 | Нарушение приёма сумки от инкассатора | инкассатор уходит до проверки сумки | [231] подп. 3), 4) п. 24, п. 25 | трактовка |
| T8 | Подозрительные манипуляции с наличными | купюра уходит к одежде/рукаву | [231] п. 12, п. 20 | трактовка |
| T9 | Не проведена идентификация клиента | наличные без предъявления удостоверения или цифрового документа | [231] подп. 1) п. 19, подп. 1) п. 31 | прямое |
| T10 | Клиент ушёл до конца пересчёта | клиент уходит, кассир ещё считает | [231] п. 20 | прямое |
| T11 | Смешение наличных разных клиентов | пачка предыдущего клиента не убрана, новая сверху | [231] п. 20, п. 21 | трактовка |
| T12 | Возврат наличных после пересчёта (требует сверки) | кассир отдаёт часть денег клиенту | [231] подп. 4) п. 19 | трактовка, нужна сверка документов |
| T13 | Ключ от сейфа оставлен без присмотра | запирает сейф и уходит с пустыми руками, ключ в замке | [231] п. 20, п. 76, п. 80 | трактовка |
| OTHER | Иное | свободное описание модели | — | требует проверки |

«Прямое» — пункт прямо регулирует наблюдаемое действие; «трактовка» — пункт регулирует близкую норму,
связь с видео — наша интерпретация (так и показывается проверяющему).

## 7. Ограничения и известные ошибки

- **Разрешение исходника 464×848.** Ключ в замке — несколько пикселей, удостоверение и купюра — десятки.
  T13 и различение «карточка / купюра» ненадёжны; для них камера должна быть ближе.
- **Ложные срабатывания** чаще всего: «нет проверки удостоверения» (T9) и «уход с рабочего места» (T1)
  в нормальных роликах; «телефон» (T4) при работе с мелкими предметами.
- **Нарушения по бездействию** (T9) — модель может пропустить короткую передачу документа или цифровой
  документ на телефоне, который разрешён п. 19 Правил [231].
- **Таймкод** у событий движения (вход/выход) может отличаться от метки на 2–5 с: модель видит окно
  с шагом 0,5 с и иногда отмечает начало действия, а иногда — его итог.
- **Новые ракурсы.** Модель не обучалась на датасете и не привязана к координатам — правила и промпты
  описывают действия, а не места в кадре; но качество на сильно другом ракурсе не измерено.
- **Разметка датасета неоднозначна**: `X-39` (норма без удостоверения) против `X-2` (нарушение);
  смысл нарушений в `X-24`, `X-28`, `X-13` установлен командой предположительно.
- Описание наблюдения пишет модель; формулировка «почему это нарушение» и норматив — из каталога.
  Если в наблюдении есть то, чего на видео не видно (оформление, суммы, намерения, обвинения), оно
  отбрасывается фильтром (`observation_ok` в `pipeline.py`) — остаются нейтральное пояснение и норматив.

## 8. Структура

```
ml/
  cashier/            продуктовый код
    pipeline.py       analyze() — точка входа, Config
    detect.py         ступень 1: окна → кандидаты
    verify.py         ступень 2: проверка кандидата (кропы, вопросы по типам)
    video.py          чтение кадров, JPEG
    catalog.py        доступ к каталогу нарушений
    violations.yaml   каталог типов + нормативы
    perception.py, rules.py   покадровое восприятие и правила (исследовательская ветка, в продукт не вошла)
  experiments/        оценка: vlm_eval (ступень 1), verify_eval (ступень 2), policy_eval (политики, без GPU),
                      load_test (5 роликов разом), timeline_eval, clf_baseline
  remote/             setup_pod.sh, serve_vllm.sh — подготовка GPU-сервера
  tests/              синтетические тесты правил
eval/labels.csv       разметка датасета командой (типы, сомнения, дубликаты)
```
